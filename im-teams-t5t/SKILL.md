# T5T Skill

## 角色与核心原则

帮助用户生成“下周 T5T”、修改已有 T5T，或查询/浏览已填写的 T5T，把散乱材料收敛成少量、真实、可读、按优先级排序的工作重点，并在用户确认后写入 360Teams。T5T 默认指 Top 5 Things：最多 5 条、每条一句话、不超过 80 个中文字符。

四条核心原则，全程优先级最高：

1. **生成是核心能力，接口只是提交通道。** 内容提炼完全靠模型自身，不依赖任何接口。认证或接口失败时，必须把已生成的 T5T 内容完整交付给用户并给出手动提交指引（见「失败与认证分支协议」），绝不能因为接口不通就什么都不交付。
2. **失败快速分支，不重试不深挖。** 任何脚本失败后，按分支协议处理一次即停止；禁止反复重试同一命令、禁止连环调用其他接口“排查”、禁止主动去读脚本源码找原因（脚本输出的 `message` 和 `hint` 已包含可操作信息）。
   - **`status:"error"` = 终点，立刻收尾。** 脚本把结果 JSON 打到 stdout，**退出码非 0 时 stdout 一样有完整 JSON**——那就是结论。看到 `status:"error"` 的那一刻，本任务的脚本调用**就结束了**：除认证失效（`status:"expired"`/退出码 4，走认证分支）外，**一律直接走「降级交付」**。
   - **严禁这些「再试一下」动作**（看到 error 后全部禁止）：重跑同一命令、加 `2>&1`/改重定向「抓输出」、再跑 `env_check`、换 `python`/`py -3`、`--version`、列目录、跑 `query_t5t.py --latest` 之类去「确认状态」。**别拿「我好像没看到输出」当借口**——输出就在那、`status` 字段就是结论，重跑/重定向只会拿到同一个 JSON，白费两轮还惹审批。`message` 是网络/服务问题就照它降级，结束。
3. **前置数据只取一次，后续复用。** 同一任务内每类查询（周期、最新详情、抄送人）只调用一次，后续步骤复用已返回的数据；脚本返回里已包含的数据不要再发起新查询。payload 组装由脚本在提交时完成，代理不提前组装。
4. **后台静默。** 解释器探测、脚本调用、查询、校验、提交都是后台动作。用户只应看到：生成的内容、一次必要的确认、最终结果（或失败说明 + 手动指引）。不发“正在查询/正在核对/正在提交”等过程播报，不展示命令、脚本输出、内部术语。

脚本职责（固定配置统一在 `scripts/config.py`，代理只按配置执行）：

- `scripts/submit_t5t.py`：查询可填写周期并新建 T5T。
- `scripts/query_t5t.py`：**只读查询**——查最新已填写 T5T 详情（`--latest`）、浏览最近列表（`--list-recent`）；不修改、不提交。
- `scripts/edit_t5t.py`：编辑/更新已填写 T5T（提交修改）。
- `scripts/t5t_client.py`：共享能力，不要直接作为命令执行。

## 触发示例

| 用户怎么说 | 输入 | 应交付什么 | 易错点 |
|---|---|---|---|
| “根据这份周报帮我写下周 T5T”（附周报） | 周报文本/文件 | 生成 ≤5 条重点，确认一次后写入，展示结果和预览链接 | 编造材料里没有的事实；确认多于一次 |
| “把会议纪要整理成 T5T，直接提交” | 纪要文本 | 已授权：生成后直接提交，不再确认，展示结果 | 已授权还反复让用户确认 |
| “帮我写下周 T5T”（无任何材料） | 无 | 一句话请用户发送材料（如本周进展、下周计划） | 凭空编一版看似真实的 T5T |
| “把这 5 条压缩一下，按优先级重排” | 已有 T5T 文本 | 优化后的文本，不调用任何脚本 | 多余地探测解释器、调接口 |
| “查一下我最新的 T5T” | 无 | 展示周期、内容、抄送人、同组可见 | 查完又主动追问要不要改 N 轮 |
| “把最新 T5T 第 2 条改成 xxx，提交” | 修改指令 | 查最新→改→直接提交→展示结果 | 修改无歧义还请求确认 |
| “看看最近 5 条 T5T” | 无 | 只读列表展示后结束 | 基于历史条目发起修改 |
| “删掉最新 T5T 里张三的抄送” | 删除指令 | 查最新→确认→提交删除后的抄送人 | 新增/构造抄送人对象 |
| “这是我本周的 T5T，优化一下”→“写入” | 现有 T5T | 改的是现有内容：优化后授权写入→**直接 `--update-if-exists` 更新本周，不再弹冲突** | 又弹一次“现有 vs 新”问要不要更新 |
| “帮我写下周 T5T”（附本周作素材），最新周期其实已填 | 新材料 | 写新一版：plain 提交撞 `already_submitted`→展示对比、问“更新还是保留” | 静默覆盖现有；或只回“已填写”就停 |
| 认证失效时用户要求提交 | 内容已生成 | 拉起认证并立即发出认证链接→等认证→成功则提交；失败则交付内容+手动指引 | 不给链接让用户干等；反复拉认证 |

## 运行前置

脚本需要 Python 3.9+，且命令参数含**中文**（T5T 内容）——必须避开会截断中文的 VM shim 假 Python。所以每个任务**先跑 env_check 拿可靠的 Python 路径，再用它跑业务命令**。

**步骤零（任务第一步，先于任何业务/认证命令）：检测 Python 路径**

```bash
python3 scripts/auth/env_check.py
# 输出: {"status":"ok","python_path":"/绝对/路径/python","version":...,"platform":...,"cached":...}
```

- 用 `python3` 起这条；**仅当**它报 `command not found`/`不是内部或外部命令`、或沙箱返回非标准退出码（如 `49`，说明裸命令不可用）时，依次换 `python`、`py -3` 起同一条 env_check；三者都起不来、或 env_check 返回 `status:"error"`（没装 Python 3.9+）时：**先把已生成的 T5T 内容照常交给用户**（生成不需要 Python），再提示「装 Python 3.9+（https://www.python.org/downloads/）或确认 PATH 后我可帮你自动提交」，不反复重试。
- 从输出取 **`python_path`**：**本任务后续所有命令（submit/query/edit/auth）一律用这个绝对路径**，即下文示例里的 `{python_path}`，**严禁再用裸 `python3`/`python`**。同一会话只测一次（env_check 自带 7 天缓存，后续毫秒级返回）。

> **为什么必须这样**：① 沙箱（WorkBuddy 等）`python` 不在 PATH，裸命令返回非标准退出码（如 `49`），直接跑业务脚本会失败；② VM shim 是会**截断中文参数**的假 Python，env_check 自动排除它，保证 T5T 中文内容不被截断。

**拿到 `python_path` 后就锁定它**：后续不再跑 env_check、不再探测/切换解释器、不 `--version`、不列目录。业务脚本返回 `status:"error"`（网络/服务/认证）是**业务结果**，走「失败与认证分支协议」，与 Python 环境**毫无关系**——绝不因此重测环境或报「Python 环境未就绪」。

只生成/整理/润色内容时不运行任何命令、不读脚本和文档。

**脚本一律用绝对路径调用，不要依赖当前目录。** 下文命令里的 `scripts/xxx.py`、`scripts/auth/xxx.py` 都是相对本 skill 目录写的；shell 的 cwd 不一定在这里，直接跑相对路径会报“文件不存在”，还得多花回合去探目录。**把 `scripts/xxx.py` 换成本 skill 目录（即本 SKILL.md 所在目录）的绝对路径再执行**，例如 `{python_path} <本skill目录>/scripts/submit_t5t.py ...`（`{python_path}` 用步骤零的检测结果）。不要先去 `cd`、也不要先列目录结构猜路径。

环境保密：运行环境是内部实现细节，面向用户的回复中禁止出现环境名、`--env`、`test`、`production`、“默认环境”等字样；仅开发者明确要求排查配置时才讨论。

## 周期说明（“本周/下周”都指同一个最新周期）

T5T 的填写周期横跨两个自然周——**当前周的周四 ~ 下周三**。同一时刻系统里**只有一个最新可填写周期**。所以用户口语里的“本周”“下周”**指的都是这同一个最新周期**，不要按字面去区分本周/下周、也不要纠结选哪个周期：

- 写入/更新一律对**最新周期**操作：`submit_t5t`/`edit` 查到的（可填写周期或最新详情）就是它。
- 时间只是帮你理解用户措辞，不影响选周期：周四~周日用户多半说“下周”，周一~周三可能说“本周”，但落地都是这同一个最新周期。
- “新建还是更新”由**查可填写周期**决定（最新周期没填→新建，已填→更新），**与用户说本周还是下周无关**。

## 意图识别（第一步，先于任何脚本/认证）

收到请求先判定意图，再决定要不要碰脚本。**纯生成意图绝不触发认证、查询或任何脚本**：

- **纯生成 / 润色 / 压缩 / 整理**（“帮我写”“生成下周 T5T”“把这段整理成 T5T”“压缩重排”等，不含“提交/写入/更新/填进系统”之类意思）→ 走**路径 A**：只产出内容并交付，**不认证、不查询、不调任何脚本**。交付内容后**固定用一句话**告诉用户可以写入（如“要写入 360Teams 的话说一声，我直接帮你提交”），但不主动拉认证。**生成就是按规则直接快速产出 5 条内容，一步到位**：不要建任务列表（TaskList/任务清单）、不发进度更新、不生成任务制品（Tasks/产物文件）、不做多步流程编排或“计划→执行→汇报”那套；遵守内容规则（≤5 条、每条 ≤80 字、按优先级排序）后按「展示模板」用表格直接给用户即可。
- **用户明确没有 Teams / 无法认证 / 暂不提交**（“我没装 Teams”“先不提交”“只要内容”）→ 同样按纯生成处理，**直接跳过认证与接口**，把内容给用户；需要时说明“自动写入需要 Teams 认证”，**不空等认证、不发用不了的链接**。
- **含提交/写入意图，分两种**。关键判据：**用户给的内容，是“要被优化/修改的现有 T5T 本身”，还是“用来生成新一版的素材”？**
  - **改现有 → 直接更新（加 `--update-if-exists`）**：用户给的就是本周/最新现有 T5T、并要对它优化/润色/调整/改（“**这是我本周的 T5T，优化一下**”“润色我现有的这版”“更新我现有的 T5T”“把我已填的改成 X”），授权写入后**直接 `--commit-confirmed --update-if-exists`**，一步到位、**不要再弹冲突**——用户清楚知道有现有内容、就是要改它，再问是多余。反正只有最新一篇能编辑。
  - **写新一版 → plain，撞已填要问**：用户在写一版**新的**（“帮我写下周 T5T”“根据这份周报/纪要写一版”，给的内容是**素材**不是现有 T5T，用户没表示知道最新周期已有 T5T）→ 用 **plain `--commit-confirmed`（不加 `--update-if-exists`）**。最新周期没填→新建；已填→返回 `already_submitted`（**不写入**）→**走冲突处理**：告知“最新周期已经有一版 T5T 了”、展示对比、问要不要更新，**绝不静默覆盖**。
  - 判不准是“改现有”还是“写新”：倾向 plain（让冲突浮出来问），别贸然 `--update-if-exists` 覆盖。

  > 系统同一时刻只有一个最新可填写周期（横跨周四~下周三）。用户说“写下周”常以为是写**新的空白**，但若最新周期已填、又没新周期开放，就**没有“下周”可写**——这种新建意图撞已填要弹冲突，不默默覆盖。而“优化我本周现有的”是改现有，直接更新即可。
- **查询/浏览意图**（“查我最新 T5T”“看看我填的 T5T”“我这周填了啥”“看看最近 5 条”）→ 这是**读取已填内容**，必须调脚本（`query_t5t.py --latest` 查最新 / `query_t5t.py --list-recent` 浏览最近）、需要认证，**不是纯生成，绝不能只靠模型凭空答**；未认证就走认证补救后重试。这类请求**不含**写入，查到/展示后即结束，不主动追问要不要改。
- **意图不清**（像生成又可能要提交）→ 先按纯生成出内容，展示后按「提交意图与确认」问一次“要写入系统吗”，用户确认才进认证/提交。

一句话原则：**没有写入意图就不自动写入**——纯生成只产内容、不碰接口；但**查询/浏览是另一类意图，要调脚本读取（需认证），别把它当纯生成。**

## 任务路径总览

先判断任务类型，再走对应路径。每条路径有标准脚本调用次数，超出即说明流程走偏：

| 路径 | 标准调用次数 | 命令 |
|---|---|---|
| A 纯生成/润色/压缩 | 0 | 不调用任何脚本 |
| B 新建/更新本周 | 1 | `submit_t5t.py --commit-confirmed`（更新本周加 `--update-if-exists` 仍 1 次搞定新建或更新；多周期需用户选时 +1 次带 `--report-id` 重提；未带标志撞冲突走对比时 +1 次编辑提交） |
| C 查询最新 / 编辑最新 | 1～2 | `query_t5t.py --latest`（要改再 +1 次 `edit_t5t.py --commit-confirmed`） |
| D 浏览最近列表 | 1 | `query_t5t.py --list-recent` |
| 认证补救 | 全任务最多 1 轮认证 + 1 次原命令重试 | `auth.py --start --no-cache` 发链接后 `auth.py --wait` |

## 内容生成准则

- **用户明确要求优先**：用户点名要带的内容、重点、本周事项、侧重、口径，一律照办；下列为未指定时的默认，不得用默认削弱用户的明确要求。唯一不可逾越的是脚本硬限——≤5 条、每条 ≤80 字、`--items-json` 纯字符串数组（超限按 message 精简合并，不是忽略用户要求）。
- **材料决定内容**：有材料 → 基于材料提炼（含其中的客户反馈、市场观察、风险卡点），不加没依据的事实；只给现有 T5T → 按要求改、保留原意，不擅自新增；无材料 → 请用户发素材（本周进展/下周计划/现有 T5T），不编造。
- **最多 5 条、按优先级排序、去琐碎；每条一句话写清核心，充实不注水**：完整、具体、书面得体，说清该事的**进展 / 目标 / 卡点**，别甩干巴短词或半截短语；真实客观——有成绩如实说、**有问题也直接提、不回避**，润色只动表达，不堆形容词、不夸大、不包装材料没有的成果。信息照实、表达讲究。
- **先看场景再决定能不能改信息（按内容性质判断，别只认「润色」这个词——用户说改一改/调整/顺一顺/精炼/换个说法/优化/帮我看看/写得更…，措辞千变万化，本质都看下面两类）**：
  - **A 加工现成内容**（给的是现有 T5T / 现成条目，让你在其上改）→ **保语意、不加料**：只改表达让它通顺利落，**绝不改变原意、绝不添油加醋**，不凭空加原文没有的信息（如「本周完成 X」「下周继续 Y」「推动团队试用」「收集反馈」这类原文没说的节点/动作），不硬塞「本周 → 下周」时间结构，既不强转成「已完成」过去式、也不编造未来动作；用户指定改某维度（更简洁/更突出结果/换语气等）就只动那一维度，没指定别多动。
  - **B 从素材生成**（给的是周报/纪要/进展/要点等素材，让你产出 T5T）→ **提炼成工作重点**：动作化表述（推进/对接/上线/完善），基于材料合理组织、可从材料顺延，但不编造材料毫无线索的事实。
  - 判不准是 A 还是 B → 按 A 处理（保原意），别贸然按 B 重写加料。承接「本周成果 → 下周动作」只在原文本就含跨周信息、或用户明确要求时才写。
  - 例（A 保语意）：原「探索 X 封装落地，覆盖 A/B/C，初步形成闭环」→ ✓「推进 X 封装与落地，覆盖 A/B/C，初步形成流程闭环」（只理顺表达，信息不增不减）；✗「本周完成 X，下周推动团队试用并收集反馈」（编造了原文没有的本周完成/下周动作＝加料）。
- **一稿成型、别墨迹**：直接写 1～5 条交付，不反复重写/列多版/来回自审。**绝不逐字数长度**——写完直接交，长度由脚本拦截、超了再精简，生成时一个字都不用数。条数按材料实有写（够 3 条就 3 条，不硬凑 5、不为补满注水）。**场景 B（从素材生成）**时，下周动作从材料自然顺延属合理延伸、不算编造（只有凭空发明材料毫无线索的新事项才算编造）；**场景 A（加工现成内容）保语意、不加料、不编造，以上一条为准**。
- **产出形态**：按「展示模板」用表格展示（`| # | 内容 |`）；不加长篇背景；条数/字数/排序是后台规则，不对用户解释或承诺；调整/优化后只给新版内容，不列「改动说明」、不展开对比（要说一句带过）。

脚本会强制校验：超 5 条拒绝、单条超 80 字报错、不足 5 条自动补空（写实有条数即可，补的空串只占位、不展示，少写无需纠结）。

## 提交意图与确认

- 用户说“提交”“写入”“直接提交”“直接更新”“修改后提交”等，或上下文已清楚表达提交意图：视为已授权，无冲突时直接执行到完成，**不展示内容请求确认**。
- 用户只要求“生成/整理”：展示内容后用一句话确认一次（如“要把这版写入系统吗？”），确认后连续完成提交，不再二次确认。
- **改稿指令 ≠ 提交授权**：内容尚未提交（仍在生成/预览阶段）时，用户对内容本身增删改（“把 AI 那条删了”“第 2 条换成 X”“加一条 Y”“再精简点”）是**调整内容、不是要提交**——按要求改完只给出新版内容，再用一句话确认一次（如“这版可以的话我帮你写入”），**绝不因为用户下了改稿指令就直接提交**。只有用户用提交类措辞（见首条）才视为授权。
- 修改动作有歧义、无法可靠确定最终内容：先澄清，不提交。
- 没有提交意图：绝不自动提交。

## 路径 B：新建写入

用户已授权或确认后，一次调用完成核对与提交：

```bash
{python_path} scripts/submit_t5t.py --commit-confirmed --open-preview --items-json '<T5T JSON>'
```

**只有**用户明确要**更新已有的最新 T5T**（清楚知道最新周期已有内容、并要替换它）时，才加 `--update-if-exists`，同一进程内“没填就新建、已填就就地更新”：

```bash
{python_path} scripts/submit_t5t.py --commit-confirmed --update-if-exists --open-preview --items-json '<T5T JSON>'
```

> ⚠️ `--update-if-exists` 会**静默覆盖**最新周期的现有内容、不弹冲突。判不准用户是否知道已有内容，就**别加这个标志**——用 plain `--commit-confirmed`，让 `already_submitted` 冲突浮出来再问用户。泛泛的“帮我写/写下周”不算明确授权更新。

**`--items-json` 格式（强制，必须严格遵守）**：纯字符串 JSON 数组，每个元素是一条 T5T 文本，例 `["重点一","重点二"]`。最多 5 条、每条 ≤80 字、不能有空串。**一律用纯字符串数组，不要包成对象或嵌套**（如 `[{"content":...}]` 缺 `value` 键会被丢成空、报「请至少提供一条 T5T」；`[{"value":...}]` 虽能被脚本兼容取值，但属内部回读格式，生成时别依赖，避免歧义）。生成内容时就按此格式产出，不要临时拼别的结构。

**格式校验已内置在提交里，不必单独预跑**：`--commit-confirmed` 在联网前会先本地校验 `--items-json` 格式，格式错时**不联网就秒级返回**格式错误（见失败协议）。所以正常**直接提交即可**，不要每次再单独跑一遍 `--validate-items`——那是多一个进程、多一次审批，白费。格式错时按 `message` 重新生成内容再提交，**最多 3 次**。`--validate-items`（纯本地、不联网）仅在你想完全不发起提交、只做一次格式预检时可选用，非必需步骤。

可选 `--invite-same-group true|false`（不传默认 `true`；用户明确要求同组不可见才传 `false`）。脚本内部自动完成：查周期 → 查历史抄送人 → 组装 payload → 提交。按返回分支：

- `status: ok`：提交成功。按下面「提交/更新成功展示模板」固定格式展示，抄送人和同组可见是硬性展示项，每次提交/更新成功都要带上，不能只给内容和预览链接。
- `status: period_choice`：有多个可填写周期，输出 `periods`（每项 `reportId`、`name`）。**把周期名列给用户选一个**，再带 `--report-id '<所选 reportId>'` 重跑同一条提交命令完成写入（只有一个周期时不会出现此状态，脚本已静默选用，无需询问）。
- `status: already_submitted`：本周期已写过，进入冲突处理（下节）。
- 退出码非 0：按「失败与认证分支协议」处理。

### 冲突处理：本周期已存在

> 走到这里说明你用的是 plain `--commit-confirmed`（没带 `--update-if-exists`），即你**并不确定用户知道最新周期已有内容**。所以**默认要把冲突告诉用户、让其选择，绝不静默覆盖**。脚本此时**只查不写**（`already_submitted` 不会提交），是安全的。

`already_submitted` 的返回里**已包含**最新详情（`id`、`items`、`canOperate`、抄送人、同组可见），直接复用，**不要再调 `query_t5t.py --latest`**。

1. `canOperate=false`：告知“本周期已有一版 T5T 且当前不可修改”，结束。
2. `canOperate=true` → **默认：明确告知用户“最新周期（<周期名>）已经有一版 T5T 了”，用表格对比现有内容和新内容，问一次“要更新成新版，还是保留现有？”**（措辞用“更新”，禁用“覆盖”）。对比固定用下面格式，按条目序号对齐，条数不等的一边留空，不要写成两段散文：

   | # | 现有 | 新版 |
   |:-:|------|------|
   | 1 | ... | ... |
   | 2 | ... | ... |

   - 用户选更新 → 用下面命令提交（保留原抄送人和同组可见）；用户选保留/放弃 → 结束。
   - 用户在原请求里就**已明确表示知道现有内容、要替换它**（本该第一步带 `--update-if-exists`、没带才落到这里）→ 可不再追问直接更新。**只要不确定就走告知+询问。**

```bash
{python_path} scripts/edit_t5t.py --commit-confirmed --id '<详情 id>' --open-preview --items-json '<新内容 JSON>'
```

**关键：撞到 `already_submitted` 默认意味着用户大概率不知道已有内容——先告知、展示、询问，拿到明确“更新”才提交，永不静默覆盖。** 泛泛的“帮我写/写下周”不构成更新授权。

## 路径 C：查询并编辑最新 T5T

第一步，查询（用户明确要查或要改时才执行，只读脚本）：

```bash
{python_path} scripts/query_t5t.py --latest
```

- `status: not_found`：告知没有已填写的 T5T，结束。
- `status: latest_detail`：按「展示模板」的完整记录格式展示周期、内容（表格）、权限（无则“无抄送人”）、同组可见，没有 previewLink，省略预览链接行。
  - `canOperate=false`：说明最新返回的是历史周期（最新周期还没填，只有最新周期可编辑）。若用户本是想**写/改本周**→ 改走路径 B（`submit_t5t --commit-confirmed`，会查到可填写周期直接新建）；若用户只是想看→ 展示后结束。不要只回“不可修改”就停。
  - 原请求已含明确修改动作：直接执行修改；同时含提交意图则直接提交。
  - 用户只查询：展示后结束，不追问。

第二步，提交修改。脚本会重查详情核对后提交，两种取详情方式：

- **更新最新单条（推荐，一步到位）**：用 `--latest`，自动定位最新→核对→提交，无需先单独查 id：

```bash
{python_path} scripts/edit_t5t.py --commit-confirmed --latest --open-preview --items-json '<修改后完整 T5T JSON>'
```

- **已知具体 id**（如刚用 `query_t5t.py --latest` 拿到，或要改的不是最新单条）：用 `--id`：

```bash
{python_path} scripts/edit_t5t.py --commit-confirmed --id '<详情 id>' --open-preview --items-json '<修改后完整 T5T JSON>'
```

- `--items-json` 同样遵守路径 B 的**强制纯字符串数组格式**（`["改后内容一",...]`，最多 5 条、每条 ≤80 字、无空串、不包对象）。格式校验已内置在提交里（不联网先校验），**不必单独预跑 `--validate-items`**；格式错按 `message` 重新生成再提交，最多 3 次。
- 删抄送人：传 `--to-list-json '<删除后的完整 toList JSON>'`（只能从详情 `toList` 删除整对象，人数必须严格少于当前；不删就不传）。
- 切换同组可见：传 `--invite-same-group true|false`（不传保留原值）。
- 只改内容不传 `--to-list-json`；只删人不传 `--items-json`；三类修改可任意组合；三者都不传脚本会拒绝。
- 用户要求**添加**抄送人：明确告知没有可靠人员数据来源，无法添加；不得查询、猜测或构造人员对象。

{python_path} scripts/query_t5t.py --list-recent --page-size 5

## 失败与认证分支协议

这是本 skill 的硬性协议。脚本退出码：`0` 成功（含 `already_submitted`）、`1` 业务/系统错误、`4` 认证失效（`scripts/auth/auth.py --wait` 额外有 `3`=认证仍在进行中，见下节）。脚本无论成败都把结果 JSON 打到 stdout，`message`/`hint` 已说明原因和下一步，照做即可、不要自行发明排查流程。**拿到任何一段 JSON（含 `status:error`）就是收到结果，按下面分支处理——别重跑、别加 `2>&1` 抓输出（见核心原则 2）。** 这些 JSON、`message`、`hint`、命令都是内部信息，绝不原样展示给用户。

### 认证失效（退出码 4 / status `expired`）

触发范围：脚本按统一网关码表（`scripts/auth/gateway_errors.py`）识别认证失效——除 HTTP 401/403 外，**登录过期、账号异常等业务码（如 10230/10301/12001/12003/12004/10220/10241）也会自动判为认证失效**，即便本地 token 还没到过期时间。处理方式都一样：走下面的两段式认证，`--no-cache` 会先删掉本地 stale token 再重新获取。

两段式认证，**第一步必须先把链接发给用户、作为这一轮对话里能看到的一条消息，再去调 `--wait`**——不允许先连续调脚本、等拿到 `--wait` 结果才把链接亮出来，那样用户全程看不到链接、只会觉得在空等：

1. **拉起认证**（秒级返回；当前在受限沙箱时应申请非沙箱执行，认证需要监听本机端口）。**必须带 `--no-cache`**：业务命令退出码 4 既可能是本地没有 token，也可能是本地 token 看似有效但已被服务端作废——不清缓存会被「本地有效」短路而跳过真认证：

```bash
{python_path} scripts/auth/auth.py --start --no-cache
```

   - `status: error`：不重试，走降级交付并说明可稍后再试。
   - `status: pending`：**拿到这个返回结果后，下一步必须是发一条消息给用户，禁止在发消息之前先调用 `--wait` 或任何其它工具**。消息里用 `appLinkUrl` 作「在 Teams 中打开认证」（https 链接，任何客户端都可点）；输出**包含 `landingUrl` 字段时**才附加浏览器那一行（没有就不提浏览器）。**`schemeUrl`（teamssit:// 协议链接）多数客户端点不开，仅供脚本内部自动拉起，不要发给用户。** **整个认证全程只拉起一次、只发一次链接**：`--start` 已自动弹出一次认证窗口并返回链接，你只需把链接发给用户一次，**不要重复 `--start`、不要多次触发打开、不要反复发同一条链接**；窗口被关掉时让用户点已发的同一条链接重开即可，无需你再拉起。话术：

```text
需要先完成一次认证，我已尝试拉起 Teams 认证窗口。如果窗口没有弹出、或不小心被关掉了，点下面的链接重新打开：

- [在 Teams 中打开认证](<appLinkUrl>)
- [在浏览器中打开认证](<landingUrl>)   ← 仅当输出包含 landingUrl 时附加这一行

完成授权后我会自动继续。
```

2. **链接发出去之后**，按下面的节奏等结果，**别一次阻塞到底、也别按秒数无限短轮询**：

```bash
{python_path} scripts/auth/auth.py --wait --poll-timeout 8
```

   - 退出码 `0`（`status: ok`）：重试原业务命令**一次**。仍失败 → 停止一切接口调用，走降级交付。
   - 退出码 `3`（`status: pending`）：**认证会话仍有效，不是失败、不要降级、不要重新 `--start`**。**第 1 次**用 `--poll-timeout 8`（基本必定 pending，真人不可能 8 秒内点完认证，这次只是确认流程往下走）；**之后每次**改用 `--poll-timeout 60` 重复调用，**直到返回 `ok`/`expired`/`error` 为止**——不要自己设固定次数或秒数上限提前喊停，会话真实到期时间由 `scripts/auth/config.py` 的 `RECEIVER_TIMEOUT_SECONDS` 决定，脚本到点会自然吐 `expired`，这个节奏不用跟着它手动同步。每次 `--poll-timeout 60` 返回后才对用户说一句简短的「还在等」，把返回里的 `remainingSeconds` 换算成大概分钟带上（如“还在等你完成认证，链接大概还有 X 分钟过期”），不要只说一句空泛的「还在等」；不要中途反复刷屏。
   - 退出码 `4`（`status: expired`，会话彻底超时）：告知认证未完成，走降级交付，并说明“完成认证后告诉我，我再帮你提交”。
   - 退出码 `1`：走降级交付并说明可稍后再试。

3. **全任务最多发起一次 `--start`**（同一轮认证内多次 `--wait --poll-timeout 8` 轮询不算重新发起）；遇到退出码 `4` 后不再认证，直接降级交付。用户说“认证好了/重试”时可以再来一轮（重新从 `--start` 开始）。
4. 窗口被误关时点已发链接重开即可（不重新认证）；仅当链接已失效，才再跑一次 `--start` 取新链接发给用户。

### 业务/系统错误（退出码 1 / status `error`）

提交是有先后顺序的接口链（查周期 → 查抄送人 → 提交），**任一步失败即停，不回头、不重复尝试**：

- **接口失败 / 超时 / 网络 / HTTP 5xx / 任何返回 code≠0**：一次失败立即停止，**不重试、不为抓输出重跑（含加 `2>&1`/改重定向）、不换解释器、不探测 Python 环境、不列目录、不调其他接口排查、不读脚本源码**（脚本已返回 JSON，stdout 里就是完整结果，解释器是好的，这是业务失败不是环境问题），直接中止提交走降级交付，并在提示里**点名是哪一步没成功**（脚本 `message` 已含步骤名：「获取周期列表」「获取历史抄送人」「查询 T5T 详情」「提交 T5T」等，照搬步骤名即可，不要带 code 数字或接口路径）。
  - **按原因给用户不同说法**（看 `message`）：
    - 含「网络连接失败」→ 明确告诉用户是**网络问题**，让其检查网络、稍后再试。
    - 「服务暂时不可用」「接口返回异常」→ 告诉用户**系统暂时不可用 / 内部出了点问题**，稍后再试；不暴露 code、HTTP 状态、接口路径。
    - `{某步骤}失败：{服务端原因}`（服务端给了人话原因）→ 可把这句人话原因转述给用户。
    - 收尾统一加一句「稍后可以再让我试一次」，此时本轮对话已结束。
- **提交内容格式错**（`message` 指出 JSON 格式、超 5 条、超 80 字、「请至少提供一条 T5T」等）：提交命令在联网前已就地校验格式，**格式错是不联网就秒级返回的，没有浪费接口**。按 `message` 重新生成内容后**直接再提交**，含首次在内**最多 3 次**；3 次仍不合格 → 停止，降级交付并提示用户。无需单独跑 `--validate-items`（除非你想完全不发起提交、纯本地预检）。

### 降级交付（任何失败路径的统一收尾）

把已生成的内容完整交给用户 + 一句话说明 + 手动路径，例如：

```text
这版 T5T 已经为你整理好：

| # | 内容 |
|:-:|------------|
| 1 | ... |
| 2 | ... |

系统暂时没能自动提交（认证未完成 / 服务暂时不可用）。你可以在 Teams 的 T5T 页面手动粘贴提交；或者稍后告诉我，我再帮你提交一次。
```

不展示退出码、status、脚本名、code 数字、接口路径、`message`/`hint` 原文等内部细节；失败原因用一句平实的话概括，并**点名是哪一步没成功**（如「获取周期列表这一步没成功」「提交这一步没成功」），让用户知道卡在哪。

查询、浏览这类**没有待交付内容**的任务失败时，不套用上面的模板：一句话说明暂时查不到，请用户直接在 Teams 的 T5T 页面查看，或稍后再让你查一次。

## 成功标准

每次任务结束前自检：

- 内容：≤5 条、每条一句话且 ≤80 字、按优先级排序、无编造、保留关键成绩/目标/卡点。
- 交互：用户明确提交意图 → 0 次额外确认；未明确 → 恰好 1 次确认；写入冲突 → 展示对比 + 1 次选择。
- 调用：脚本调用次数不超过「任务路径总览」的标准次数 + 认证补救额度；同类前置数据没有重复查询。
- 失败：认证最多拉起 1 次；同一命令最多重试 1 次；任何失败都交付了生成内容和手动指引，没有空手而归。
- 输出：用户只看到内容、必要确认、结果或失败说明；没有过程播报、命令、内部术语、环境名。
- 提交/更新成功：按「提交/更新成功展示模板」固定格式，带齐周期、内容、抄送人（无则“无抄送人”）、同组可见、预览链接——抄送人和同组可见不能漏。
- 写入冲突对比：用表格按条目序号对齐展示现有 vs 新版，不写成两段散文。

## 边界

- **必须停止（不再调接口）**：认证 1 轮后仍失败 / 重试原命令 1 次仍失败 / `canOperate=false` / 用户在冲突对比后不选更新。
- **必须先问用户**：无参考材料；撞 `already_submitted`（告知已有、展示对比、问“更新还是保留”，绝不静默覆盖——除非用户原请求就明确要更新现有）；修改动作有歧义。
- **必须先有授权**（明确提交意图或一次确认）才写入/更新。
- **禁止**：新增/替换/构造/修改抄送人对象（新建只用 `latest/copies` 返回值，编辑只删已有）；代理自拼或改 payload（只能脚本生成）；基于浏览列表的历史条目改；周期列表为空还新建；向用户暴露 `Authorization`/token/环境名/内部术语（`--commit-confirmed`/`payload`/`status`/脚本名等）；用户已确认还再问、未表意图就自动提交。

> `--check`（只查周期）、`--dry-run`+`--skip-confirmation`（两阶段提交）仅开发排查用，常规不走；走时内容/周期/权限/确认哈希须一致。
