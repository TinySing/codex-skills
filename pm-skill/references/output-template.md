# PM Skill 输出参考

按任务选择结构，不要机械套用。信息不足时以需求收敛式对话澄清为主；信息充分后默认输出完整 PRD 并落盘到当前项目目录的 `prd.md`。正式 PRD 是 PM 的单一事实源；UI、架构和研发继续拆解时，应基于 PRD 转交对应 skill，而不是由 PM 直接产出专业 handoff。

## 需求收敛式澄清对话

适用场景：用户只给一句话想法，或关键信息不足以支撑完整 PRD。

- 我当前理解的需求
- 已确认信息
- 仍缺少的关键信息
- 本轮 3 到 5 条关键决策建议
- 每条使用“编号 + 小标题 + 结论 + 理由 / 影响”的格式
- 结尾说明：如果没问题请确认；如果要调整，请按编号说明修改意见

要求：

- 用对话语气给收敛方案，不要直接输出 PRD。
- 不要一次抛出过多问题。
- 不要让用户每一项都做选择题。
- 除非无法可靠推荐，否则不要列多个选项让用户逐项选择。
- 不要让每条都以“推荐...”开头，要用小标题承载决策主题。
- 推荐格式：`1. 端形态：Web 端 MVP。理由：验证成本低，适合先跑通核心体验。`
- 不要把讨论前提写成已确认事实。
- 不要在澄清阶段输出“产品规划确认稿”替代 PRD。

## 文档评审和优化

适用场景：用户给出现有 PRD、需求说明、会议纪要或多个相关文档。

先判断：

- 目标、范围和非目标是否清楚
- 用户、角色、权限和业务对象是否清楚
- 核心流程、分支、异常和边界条件是否完整
- 页面 / 模块范围是否足够 UI 承接
- 业务规则、状态流和业务不变量是否足够架构 / 研发承接
- 验收标准是否可测试
- 是否存在冲突、重复、技术越界或范围膨胀

优化输出应直接给可执行修改建议，或在用户要求时改写成正式 PRD。

## 正式 PRD

默认写入当前项目目录的 `prd.md`；用户指定文件时按用户指定路径写入。

- 文档信息
- 版本记录
- 背景、问题定义和产品目标
- 成功指标和结果衡量方式
- 关键产品决策与规划前提
- 范围、非目标、延后项和优先级分层
- 目标用户、角色和使用前提
- 术语表、业务对象和状态枚举
- 核心场景和关键任务路径
- 页面 / 模块范围和页面地图
- 功能需求：入口、触发、前置、主流程、分支、结果、异常、重复操作
- 业务规则、权限边界和状态处理
- 页面 / 模块状态矩阵
- 关键组件 / 信息单元清单
- 反馈文案规则和提示时机
- 非功能要求
- 验收标准
- 需求追踪表
- 下游交接输入
- 发布说明与复盘口径

## 下游交接输入

写在 PRD 中，不单独替 UI、架构或研发产出专业文档。

给 UI：

- 页面 / 模块清单与页面职责
- 页面目标、主任务和信息优先级
- 关键用户路径和交互约束
- 必须覆盖的状态和异常
- 关键文案与提示时机

给架构 / 研发：

- 业务对象、关键字段语义和状态枚举
- 角色、权限和前置条件
- 核心流程、分支流程、异常流程和重复操作规则
- 业务不变量、边界条件和数据一致性要求
- 验收标准、上线边界和业务依赖

## 需求评审

- 结论：合格 / 不合格，优秀 / 不优秀
- 是否可交给 UI
- 是否可交给架构
- 是否可交给研发继续拆技术契约
- Findings：按严重度排序，每条含问题、影响、建议、验证方式
- 主要缺口
- 修改优先级

## 输出自检

- 信息不足时是否只做对话澄清，没有提前输出正式 PRD。
- 澄清时是否默认给带小标题的收敛方案，而不是让用户逐项选择。
- PRD 输出时是否按规则落盘到指定文件或默认 `prd.md`。
- 每个 P0 需求是否都有入口、前置、主流程、异常和验收。
- 是否有明确不做项，避免下游扩大范围。
- 是否覆盖空态、失败、重复操作、无权限和边界输入。
- 是否只做 PM 职责内的产品定义，没有替 UI 或技术做专业方案。
- 正式 PRD 是否只保留可交付结果，没有保留讨论中途栏目。
